# ADR-0006：Android Provider 预检与冲突确认

- 状态：Accepted
- 日期：2026-08-31
- 决策范围：日历冲突、重复联系人、联系人消歧与覆盖差异

## 背景

PRD 要求 Calendar/Contacts Provider 既用于读取设备现状，也用于写入已确认行动。创建会议前必须显示疑似重复会议；创建联系人前必须搜索候选并允许继续创建或改为更新；更新联系人必须唯一确定目标并显示字段级旧值、新值和来源。当前只在写入时使用 Provider，无法证明这些确认发生在副作用之前。

Provider 读取结果可能随其他 App 操作而变化，不能由服务端模型猜测，也不能永久当作云端事实。与此同时，联系人目标或更新差异一旦改变，就会改变外部写入内容，必须使旧确认失效。

## 决策

### 1. 预检发生在服务端确认之前

Android 对每张可审核卡片提供“检查设备数据”动作，并按卡片类型请求最小读取权限。预检读取当前目标账户、可能重复项、候选联系人和相关字段；没有完成预检的卡片不能在 Android UI 中确认。

预检结果以 `(actionCardId, version)` 为键，仅保存在当前账户的设备状态中。卡片编辑、账户切换、权限撤销或 Provider 数据变化都会使结果失效并要求重新预检。WorkManager 不执行 Provider 预检，也不自动放行冲突。

### 2. 会议冲突需要显式二次确认

Calendar Provider 在目标日历的拟议时间范围内查询重叠事件，展示标题、起止时间和事件 ID。没有冲突时当前版本标记为已预检；有冲突时，用户必须明确选择“仍然保留本次会议”，才允许继续确认。

冲突放行只授权当前卡片版本和目标日历；任一字段或目标日历改变后必须重新查询。

### 3. 创建联系人提供继续创建或改为更新

Contacts Provider 优先按规范化电话或邮箱精确匹配，再以姓名作为候选提示。发现候选时显示联系人 ID、姓名、账户和匹配字段：

- “继续创建”只放行当前创建卡片版本；
- “改为更新”把用户选中的唯一联系人、字段级旧值/新值和数据行标识写回为新的 `update_contact` 卡片版本，旧确认失效，然后重新预检和确认。

姓名匹配永远不能自动选择联系人。多个候选必须由用户点选。

### 4. 更新只应用展示过的字段差异

更新卡片使用结构化 `changes`，每项包含字段类型、旧值、新值、目标 Data row（更新已有值）或 RawContact（新增值）以及来源引用。Android 在预检时再次读取旧值；若旧值已变化、目标行不存在或联系人不唯一，则阻止确认并重新生成差异。

Provider executor 只执行 `confirmedSnapshot` 中的这些变化：未列出的字段保持不变，覆盖非空旧值前必须已有当前版本的显式预检。一次 batch 的实际更新数量不符合预期时返回失败回执，不生成虚假成功。

### 5. 设备数据最小化

候选列表和未选择的联系人/日历内容不上传。只有用户选中的 Provider ID、目标账户和确认所需字段差异进入 Action Card 新版本及执行回执。Provider 数据不直接进入 Memory；若未来将成功结果形成事实记忆，只能引用确认快照和成功回执。

## 后果

- Android 确认按钮依赖当前版本的 Provider 预检，不能只依赖服务端 `ready` 状态。
- Action Card 编辑 API 需要支持在用户选择后将 `create_contact` 转为 `update_contact`，并继续使用版本冲突保护。
- 预检是时间点快照。执行器仍需在写入前验证目标行和旧值，防止预检与写入之间的竞态。
- 权限拒绝仍产生 `cancelled` 回执；预检失败本身不执行写入，也不产生成功回执。

## 验证要求

- 领域测试证明版本变化会使预检失效，未预检不能确认，冲突未经二次确认不能执行。
- Provider 测试覆盖会议重叠、电话/邮箱精确匹配、同名多候选、旧值变化和只更新所选字段。
- Compose 测试覆盖继续创建、改为更新、候选选择和会议冲突二次确认。
- 真实设备测试覆盖多联系人账户、多日历账户、权限撤销和 Provider 并发变化。
