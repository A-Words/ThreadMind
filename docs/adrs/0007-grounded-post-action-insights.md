# ADR-0007：按上下文召回并生成执行后洞察

- 状态：Accepted
- 日期：2026-09-04
- 范围：接续 ADR-0004，分小步补齐执行后推理，保持独立回滚点

## 决策

1. 成功回执仍是正式洞察的前提。输入从同账户已确认卡片、成功回执、当前 Extraction 和有效 Memory 组装，不从 InsightHistory 召回事实。
2. 记忆先在数据库按当前 submission 来源或人物引用筛选，再按更新时间排序并限制为最多 30 条；不再先取账户最近 100 条。只召回 active、有可展示来源的记录。人物候选来自已确认的姓名、联系方式、目标联系人、会议参与人及当前截图参与人，不能从任意卡片字段递归搜字符串。姓名匹配仅是候选关系，不等于跨设备或跨截图身份确认。
3. 模型只能引用服务端提供的证据键。展示摘录由服务端回填，拒绝不存在的证据、以推断支撑确定事实、超出依据的置信度；需要语义判断的帮助度与事实蕴含仍由独立评测验收，结构校验不能代替它。
4. 推理输入保留当前上下文、记忆断言及事实/推断、版本和来源。用户修正后的活动断言优先，原始来源只说明来历，不能覆盖修正。历史洞察是生成时快照，重复成功回执返回同一历史；纠错、删除影响后续新生成。
5. 生产模型必须显式配置，规则生成器保留为明确标识的开发基线。模型失败不应伪装成生成成功，不自动换供应商。回执已经持久化时，重试必须复用原 receiptId，不能重新执行 Provider。
6. 最新设备联系人快照尚未进入云端上下文。本阶段不把模型参与人或卡片字段标为真实通讯录资料；后续单独实现最小范围的、与确认动作绑定的设备只读快照及权限/时效说明，不上传整本通讯录。

### 联系人快照补充决策（2026-09-04）

Android 在 Provider 写入成功后、上报同一成功回执前采集一次有界快照。创建或更新联系人只按 Provider 返回的目标 Contact ID 读取；会议只按确认卡片内的参与人邮箱或电话精确查询，不枚举通讯录。每次最多 10 个候选，每个候选最多 3 个邮箱和 3 个电话，只包含显示名、公司、职位和上述联系方式；不上传备注、地址、RawContact 账户、头像或整本通讯录。

快照随成功回执持久化，包含 `source=android_contacts_provider`、UTC 读取时间、`granted/denied/not_required/unavailable` 权限状态、查询依据和每个候选的匹配依据。回执重放必须返回第一次持久化的快照，不能用重试载荷替换它。失败和取消回执不接受联系人记录。

Provider 写入返回的 Contact ID 可以将创建/更新动作绑定到该记录；精确邮箱或电话只能形成候选；纯显示名始终为未验证候选。同名、多条精确命中或截图人物名相同都不能自动认定为同一人，模型必须显式保留歧义并建议用户核对。

## 分步交付与验收

- 第一步：按账户、人物和来源召回，接入完整当前 Extraction；证明 100 条新无关记忆不遮蔽旧相关记忆，修订、删除、其他账户不污染后续生成。
- 第二步：接入可替换的模型洞察生成器和证据校验；证明多条记忆与当前上下文进入真实调用契约，伪造引用被拒绝，回执重放幂等。
- 第三步：设备联系人资料、独立可恢复洞察作业，以及真实模型/Android Provider 全链路质量验收。未完成前不宣称产品目标全部达成。

无新向量库或数据表。先完成有界查询和证据约束，规模性能与身份解析另行用运行数据决策。
